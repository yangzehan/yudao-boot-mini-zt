## 简介
本文档详细描述了用户管理系统中的核心实体AdminUserDO，该实体用于管理后台用户的完整信息。AdminUserDO不仅包含了用户的基本信息，还通过多对多关系与角色、部门和岗位等实体建立了关联。文档将深入分析该实体的各个字段、关联关系、ORM映射配置以及数据访问机制，为开发人员提供全面的参考。

## AdminUserDO实体字段详解

AdminUserDO实体定义了管理后台用户的所有属性，每个字段都有明确的业务含义和数据约束。

**用户ID (id)**
- 数据类型: Long
- 约束条件: 主键，自增
- 业务含义: 用户的唯一标识符，用于系统内部的用户识别和关联

**用户账号 (username)**
- 数据类型: String
- 约束条件: 唯一，非空
- 业务含义: 用户登录系统的账号，通常为字母数字组合，用于身份验证

**密码 (password)**
- 数据类型: String
- 约束条件: 加密存储，非空
- 业务含义: 用户登录密码，使用BCryptPasswordEncoder加密器进行加密存储，确保安全性

**昵称 (nickname)**
- 数据类型: String
- 约束条件: 可为空
- 业务含义: 用户的显示名称，用于界面展示，可以是中文或英文

**邮箱 (email)**
- 数据类型: String
- 约束条件: 唯一，格式验证
- 业务含义: 用户的电子邮箱地址，用于接收系统通知和找回密码

**手机号 (mobile)**
- 数据类型: String
- 约束条件: 唯一，格式验证
- 业务含义: 用户的联系电话，用于短信验证和紧急联系

**用户状态 (status)**
- 数据类型: Integer
- 约束条件: 枚举值，非空
- 业务含义: 用户账号的启用状态，0表示禁用，1表示启用

**头像 (avatar)**
- 数据类型: String
- 约束条件: 可为空
- 业务含义: 用户头像的URL地址，用于个性化展示

**部门ID (deptId)**
- 数据类型: Long
- 约束条件: 外键，可为空
- 业务含义: 关联的部门ID，表示用户所属的组织部门

**岗位ID (postIds)**
- 数据类型: Set<Long>
- 约束条件: 集合类型，可为空
- 业务含义: 用户担任的岗位ID集合，支持一人多岗

**租户ID (tenantId)**
- 数据类型: Long
- 约束条件: 继承自TenantBaseDO，非空
- 业务含义: 多租户环境下的租户标识，用于数据隔离

**其他字段**
- sex: 用户性别，枚举类型
- remark: 备注信息，可为空
- loginIp: 最后登录IP地址
- loginDate: 最后登录时间
- createTime: 创建时间，自动填充
- updateTime: 更新时间，自动填充
- deleted: 逻辑删除标志，0表示未删除，1表示已删除

## 关联关系分析

AdminUserDO实体通过多种关系与其他核心实体建立了联系，形成了完整的用户管理体系。

### 与角色的多对多关系
用户与角色之间是多对多关系，一个用户可以拥有多个角色，一个角色也可以分配给多个用户。这种关系通过中间表UserRoleDO实现：

- **UserRoleDO**: 包含userId和roleId两个字段，作为用户和角色的关联表
- **查询方式**: 通过用户ID查询其所有角色，或通过角色ID查询所有拥有该角色的用户
- **业务场景**: 权限控制、角色分配、权限继承等

### 与部门的关联关系
用户与部门之间是一对一关系，每个用户只能属于一个部门：

- **DeptDO**: 部门实体，包含部门ID、名称、负责人等信息
- **deptId字段**: AdminUserDO中的deptId字段作为外键指向DeptDO的id
- **业务场景**: 组织架构管理、部门权限控制、部门负责人设置等

### 与岗位的多对多关系
用户与岗位之间是多对多关系，支持一人多岗：

- **UserPostDO**: 岗位关联表，包含userId和postId两个字段
- **postIds字段**: AdminUserDO中的postIds字段存储用户的所有岗位ID
- **业务场景**: 岗位管理、职责分配、岗位权限等

### 与租户的关联关系
在多租户环境下，用户与租户之间是多对一关系：

- **TenantDO**: 租户实体，包含租户ID、名称、联系人等信息
- **tenantId字段**: 继承自TenantBaseDO，用于标识用户所属的租户
- **业务场景**: 多租户数据隔离、租户管理、租户配额控制等

## ORM映射配置

### ResultMap定义
AdminUserDO的ORM映射通过MyBatis Plus的注解方式实现，主要配置如下：

- **@TableName**: 指定数据库表名为"system_users"
- **@TableId**: 标识id字段为主键
- **@TableField**: 用于特殊字段的映射配置
  - typeHandler = JacksonTypeHandler.class: 用于postIds字段，将Set<Long>集合序列化为JSON存储
  - autoResultMap = true: 启用自动结果映射

### 关联查询实现
关联查询通过MyBatis Plus的Wrapper机制实现，主要方法包括：

- **selectByUsername**: 根据用户名查询用户
- **selectByEmail**: 根据邮箱查询用户
- **selectByMobile**: 根据手机号查询用户
- **selectListByDeptIds**: 根据部门ID集合查询用户列表

这些查询方法都继承自BaseMapperX，支持链式调用和条件构造。

## 逻辑删除与时间戳处理

### 逻辑删除字段 (deleted)
系统采用逻辑删除而非物理删除的方式管理用户数据：

- **deleted字段**: 继承自BaseDO，类型为Integer
- **值含义**: 0表示未删除，1表示已删除
- **查询过滤**: 所有查询自动过滤deleted=1的记录
- **恢复机制**: 可通过更新deleted字段值恢复已删除的用户

### 自动填充的时间戳字段
系统提供了createTime和updateTime两个时间戳字段的自动填充机制：

- **createTime**: 记录实体创建时间，插入时自动填充
- **updateTime**: 记录实体最后更新时间，插入和更新时自动填充
- **实现方式**: 通过MyBatis Plus的自动填充功能，在实体操作时自动设置时间值
- **业务价值**: 便于审计追踪、数据分析和操作日志记录

## 数据访问操作

### 基于BaseMapperX的CRUD操作
AdminUserDO的数据访问通过继承BaseMapperX接口实现，提供了丰富的CRUD方法：

- **插入操作**: insert、insertBatch
- **查询操作**: selectById、selectList、selectPage
- **更新操作**: updateById、updateBatch
- **删除操作**: deleteById、deleteBatch

BaseMapperX在MyBatis Plus原生接口基础上进行了扩展，增加了更多实用方法。

### QueryWrapperX查询构建器
QueryWrapperX是QueryWrapper的增强版本，提供了更灵活的查询构建能力：

- **条件方法**: 提供了eqIfPresent、likeIfPresent等条件方法，只有在参数存在时才添加查询条件
- **链式调用**: 支持流畅的链式调用语法
- **分页支持**: 内置分页功能，简化分页查询代码
- **排序功能**: 支持orderByDesc等排序方法

### 典型查询示例
```java
// 根据用户名查询用户
AdminUserDO user = adminUserMapper.selectByUsername("admin");

// 分页查询用户列表
PageResult<AdminUserDO> pageResult = adminUserMapper.selectPage(
    new PageParam(1, 10),
    new LambdaQueryWrapperX<AdminUserDO>()
        .likeIfPresent(AdminUserDO::getUsername, "张")
        .eqIfPresent(AdminUserDO::getStatus, 1)
        .orderByDesc(AdminUserDO::getId)
);
```
